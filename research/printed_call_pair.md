# Printed tool JSON, no MCP result

One goose session, 28 September 2026, `ollama` / `llama3.1:8b`, rci-knowledge.
Same question both turns: look up MPFS for CPT 99213 and report the HCPCS code.

| Arm | What happened | Trace |
|---|---|---|
| Unexecuted | The model printed `{"name": "rci-knowledge__lookup_mpfs", "parameters": {"code": "99213"}}`. Goose showed no `▸ lookup_mpfs` line. | `examples/unexecuted.json` |
| Executed | Goose called `lookup_mpfs` with `code: 99213` and the server returned that code. | `examples/supported.json` |

The cooperative gesture is the same: the right tool, the right code. Execution is what varies.

`follows-from` reads the trace. The unexecuted arm has no `tool_result`, so the verdict is `INSUFFICIENT_EVIDENCE`. The executed arm matches `results.0.hcpcs_code` and is `SUPPORTED`.

`follows_from.probes.transcript_reader` is the other method. It reads only the printed JSON. It treats `parameters.code` as the evidence that the call returned that code. On both arms it returns `SUPPORTED`.

The disagreement is the unexecuted arm. A method that reads the transcript blesses a call that never reached the server. The trace checker does not.

This is one session on one local model. It is not a rate, and it is not a claim that the class is new. The probe makes the pair reproducible: same printed gesture in, two traces out, two methods scored.

## The class

The reader returns `SUPPORTED` when the printed `parameters.code` equals the value the action claims. It never reads a `tool_result`. The checker does.

`follows_from.probes.class_score.score_printed_call_class` holds that printed JSON fixed and scores five traces. Four are captures. `result_disagrees` is the captured supported trace with `results.0.hcpcs_code` set to `99214` and the claim left at `99213`. That row was not a goose session.

| Shape | Checker | Reader | Overclaim |
|---|---|---|---|
| `executed` | `SUPPORTED` | `SUPPORTED` | no |
| `unexecuted` | `INSUFFICIENT_EVIDENCE` | `SUPPORTED` | yes |
| `tool_error` | `INSUFFICIENT_EVIDENCE` | `SUPPORTED` | yes |
| `result_disagrees` | `CONTRADICTED` | `SUPPORTED` | yes |
| `claim_disagrees` | `CONTRADICTED` | `INSUFFICIENT_EVIDENCE` | no |

An overclaim is a row where the reader says `SUPPORTED` and the checker does not. The three overclaim rows are the class: the argument echoed the claim, and the trace does not support it. The reader gives the same verdict on all three. The checker distinguishes a missing result, a failed call, and a result that is a different code.

`claim_disagrees` is the captured contradicted trace: the action claims `99214` while the print still says `99213`. The reader does not bless that claim. It is outside the class. A disagreement is not, by itself, this mislabel.

The control is `executed`. Both methods say `SUPPORTED`, so the class is not "the reader always disagrees."
